# リサーチ: 毎回同じ指示をやめる ― Claude の「スキル（SKILL.md）」を1つ作って仕事を定型化する入門

## テーマ
**決めたテーマ**: Claude Code（と claude.ai）の「スキル」入門。毎回チャットに貼っている指示を SKILL.md 1枚にまとめ、`/スキル名` や自動発動で使い回す方法を、最初の1本を作るところまで手順で解説する。

**候補3つと選定理由**
1. **Claude のスキル（SKILL.md）で「毎回の指示」を定型化する入門** ← 採用
   - 需要: 2026年に入ってから「Claude Code Skills とは」「おすすめスキル」系の解説記事・書籍が日本語でも多数出ており、検索需要が高い（note・Qiita・企業ブログで入門記事が並ぶ）[5]。
   - 独自性: 既存記事は「おすすめスキル10選」型が多い。本記事は「自分の定型作業を1本のスキルにする」手順と、発動しないときの直し方（description の書き方）に絞る。このリポジトリ自体がスキルで動く AI社員チームなので、実例を出せる。
   - 根拠: 公式ドキュメント（Claude Code Docs / Claude Platform Docs / ヘルプセンター）が揃っており、一次情報で書ける [1][2][3][4]。
2. CLAUDE.md の書き方入門（プロジェクトのルールを Claude に覚えさせる）
   - 需要はあるが、スキルとの使い分けの文脈で触れたほうが読者の得が大きいと判断し、今回は記事内の比較項目にとどめる。
3. Claude Code で小さなブラウザゲームを作る手順
   - ジャンル（ゲーム制作）には合うが、AI を使い始めたばかりの読者には環境構築の負担が大きく、1記事で完結しにくい。次回以降の候補。

## 読者
- **誰の悩みか**: Claude を使い始めたばかりの個人・フリーランス・小さなチーム。「記事の下書きルール」「コードレビューの観点」「議事録の形式」などを、毎回チャットに貼り直している／貼り忘れて品質がぶれる人。
- **よくある悩み**: 「スキルと CLAUDE.md（やプロンプト）の違いがわからない」「作ったのに発動しない」「他人のスキルを入れて大丈夫か不安」。
- **読後にできること**: 自分の定型作業を SKILL.md 1枚にまとめ、Claude Code では `.claude/skills/` に置いて `/名前` で呼び出せる。claude.ai でも ZIP でアップロードして使える。発動しないときに description を直せる。他人のスキルを入れる前に中身を確認する習慣がつく。

## 要点
- スキルは「指示・参考資料・補助ファイル」を1フォルダにまとめたもので、中心は YAML フロントマター付きの `SKILL.md`。Claude が関連すると判断したとき自動で読み込むか、`/スキル名` で手動で呼び出せる [1]。
- CLAUDE.md との違い: CLAUDE.md は常に読み込まれるが、スキルの本文は使うときだけ読み込まれるので、大きな参考資料を持たせてもトークンを圧迫しにくい [1]。
- プロンプトとの違い: プロンプトは1回きりの会話向け、スキルは「一度作れば自動で使われる」ので同じ説明を繰り返さなくてよい [2]。
- 段階的な読み込み（progressive disclosure）: ①name と description は起動時に常に読み込み（1スキルあたり約100トークン）、②本文は発動時に読み込み（目安 5,000 トークン未満）、③補助ファイルやスクリプトは必要なときだけ [2]。
- 置き場所（Claude Code）: 個人用は `~/.claude/skills/<名前>/SKILL.md`（全プロジェクト共通）、プロジェクト用は `.claude/skills/<名前>/SKILL.md`（そのリポジトリだけ）。プラグイン経由の配布もできる [1]。
- 旧来の `.claude/commands/xxx.md`（カスタムコマンド）はスキルに統合された。今も動くが、補助ファイルや自動発動の制御などはスキル形式でしか使えない [1]。
- フロントマターの基本は `name` と `description`。`name` は64文字以内・小文字英数字とハイフンのみ、「anthropic」「claude」は使えない。`description` は1,024文字以内 [2][3]。
- Claude Code では description と `when_to_use` の合計が一覧上 1,536 文字で切られる [1]。
- description には「何をするか」と「いつ使うか」の両方を書く。三人称で書く（「〜を手伝えます」ではなく「〜を処理する」）。「書類を手伝う」のような曖昧な説明は発動しにくい [3]。
- 手動専用にしたいスキル（デプロイなど副作用があるもの）は `disable-model-invocation: true` で自動発動を止められる。逆に `user-invocable: false` で `/` メニューから隠せる [1]。
- `allowed-tools` でスキル実行中に使うツールを事前許可できる（例: `Bash(git *)`）[1]。
- `$ARGUMENTS` や `$0` `$1` で `/スキル名` の後ろに書いた引数を本文に差し込める [1]。
- SKILL.md 本文は500行未満が目安。長くなったら reference.md などに分け、SKILL.md から1階層だけリンクする（深い入れ子は読み飛ばされやすい）[1][3]。
- Claude はもともと賢いので、知っていることの説明は省き、その仕事特有のルールだけ書く（簡潔さが最重要）[3]。
- 作り方のコツ: まずスキル無しで一度作業し、自分が何度も補足した情報を洗い出してから、それをスキルにまとめてもらう。Claude 自身に「このやり方をスキルにして」と頼めば正しい形式で作れる [3]。
- テストのコツ: 発動してほしい言い方を何通りか試し、発動しなければ description を直す [4]。公式は「3つ程度の評価シナリオを先に作る」ことを推奨 [3]。
- claude.ai では、スキルのフォルダを ZIP にして Customize > Skills からアップロードし、有効化する。コード実行（code execution）の有効化が必要 [4]。
- 対象プラン: ヘルプセンター（2026-07-22 更新）は Free〜Enterprise と記載 [4]、Platform Docs の概要は Pro/Max/Team/Enterprise と記載しており食い違う [2]。記事では「プランにより異なるので公式ヘルプを確認」と書く（**未確認**）。
- 面ごとに同期されない: claude.ai に上げたスキルは API や Claude Code では使えず、それぞれに用意が必要 [2]。
- 安全面: スキルは指示とコードで Claude の動きを変えられるため、自作か信頼できる提供元のものだけを使う。入れる前に SKILL.md とスクリプトを全部読み、想定外の通信やファイル操作がないか確認する [2]。
- このリポジトリの実例: `.claude/skills/ai-research/SKILL.md` など6本のスキルで「リサーチ→記事→図→校正→告知」を分担している（自作の例として紹介できる。中身は一次情報としてこのリポジトリ）。
- 「おすすめスキル○選」系の記事が多数出ているが、ランキングの根拠は各記事の主観で、本記事では扱わない [5]。

## 構成案
1. 毎回同じ指示を貼っていませんか？ ― スキルで解決できること
2. スキルとは何か：CLAUDE.md・プロンプトとの違い（図: 3段階の読み込み）
3. 最初のスキルを作る：フォルダ構成と SKILL.md の書き方（図: フォルダ構成）
4. 呼び出してみる：`/名前` と自動発動、発動しないときは description を直す
5. claude.ai で使う／他人のスキルを入れる前の安全チェック
6. まとめ：次に作るとよいスキルの例（議事録・レビュー観点・記事の型）
