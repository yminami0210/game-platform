# /review-board — 分身を一人にしないレビュー会議

分身はオーナーと同じ感性を持つので、盲点も同じになる。だから、違う物差しを持つ役を入れて揉む。

## 出席者（それぞれ別のサブエージェントとして並列に立てる）
| 役 | 物差し | 必ず答える問い |
|---|---|---|
| マーケティング担当 | 届くか・広がるか | 誰が最初の100人か。1行で魅力が伝わるか。タイトル・サムネで指が止まるか。共有したくなる瞬間はどこか |
| 副社長（COO/CFO兼務） | 続くか・網羅できているか | 稼ぐ道筋は何か。見落としている論点（法務・運用・競合・コスト）は。やめる判断基準は |
| 一般プレイヤー代表 | 楽しいか | 前提知識なしで最初の1分は楽しいか。どこで離脱するか。作り手やAIだけが楽しい部分はどこか |
| 分身（相棒本人） | 面白さの核 | 新規性と普遍性はあるか。違和感リスト（野暮・構造のための構造・目新しさだけ）に触れていないか |

各役への指示に必ず入れること: 「迎合しない。必ず懸念を2つ以上、具体的な一点で挙げる。褒めるだけの回答は無効」。

## 手順
1. **素材を渡す**: 構想メモ・指示書・成果物（URL、README、スクショ）を全員に同じものを渡す。各役は会話の文脈を持たない前提で書く。
2. **個別レビュー（並列）**: 4役それぞれが、判定（進める／直して進める／止める）、懸念、改善案を返す。
3. **議論（1往復）**: 意見が割れた論点だけを抜き出し、対立する役同士に相手の意見を見せて再反論させる。
4. **結論**: 分身が議長として統合し、決定事項・却下した意見とその理由・オーナー判断が要る点に分ける。
5. **記録**: `docs/reviews/YYYY-MM-DD-<対象>.md` に残す（役ごとの要旨、議論、結論）。
6. **反映**: 決定事項は作業指示書や子セッションへの追加指示に落とす。

## 原則
- 最後に決めるのはオーナー。オーナーにしか決められない点（タイトル決定、収益化、対外公開）は選択肢つきで上げる。
- 全員一致はむしろ疑う。一致したら「全員が見落としている前提」を議長が1つ探す。
- 報告は短く。結論 → 割れた論点 → オーナーに決めてほしいこと。
